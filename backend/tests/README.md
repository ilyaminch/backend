# Тесты backend

Набор ZTOZ-111 покрывает 12 сценариев: `AUTH-01…06` и `CHAT-01…06`.
Они реализованы в 17 тестовых методах: 8 по авторизации и 9 по чату.
С учётом параметризации pytest запускает 41 случай: 29 по авторизации
и 12 по чату. Например, защита API проверяется отдельно на 11 маршрутах,
а CSRF/Origin — в 10 сочетаниях (5 операций × 2 неверных заголовка).
С прежними семью тестами CI это 48 случаев. Набор импорта ZTOZ-107
добавляет 58 случаев по 14 сценариям `IMPORT-01…14`; полный прогон — 106 случаев.
Оформление повторяет прежние тесты: pytest, русские story и шаги Allure.

| Набор | Что проверяет | Зависимости |
|---|---|---|
| `auth/test_auth.py` | Вход, защиту API, отзыв сессии, роли, CSRF/Origin и лимит попыток | Одноразовая PostgreSQL/PostGIS БД `gis_test` с миграциями |
| `chat/test_chat.py` | Поиск, уточнение, изоляцию, повторы, ошибки и отмену | Та же БД; управляемый тестовый Dialogue, без реальной LLM |
| `imports/test_import.py` | Импорт всех слоёв, полную замену, версии, права, формат, геометрию, конфликты, лимиты, откат, таймауты и параллельные запросы | Та же БД; отдельная временная схема на каждый случай |
| `ci/test_pipeline.py` | Семь существующих проверок настройки CI | БД и Docker не нужны |

## Запуск функциональных тестов

Из корня репозитория:

```powershell
docker compose -f ops/compose.test.yml up -d --wait
```

Из внутренней папки `backend`, где находится `pyproject.toml`:

```powershell
uv sync --frozen
$env:TEST_DATABASE_URL = 'postgresql+asyncpg://gis_test:disposable_local_only@127.0.0.1:55432/gis_test'
$env:MIGRATION_DATABASE_URL = $env:TEST_DATABASE_URL
uv run --frozen alembic upgrade head
uv run --frozen pytest tests --junitxml=reports/ci.xml --alluredir=reports/allure/ci
allure serve reports/allure/ci
```

Подзадачи можно запускать отдельно: `uv run --frozen pytest tests/auth`,
`uv run --frozen pytest tests/chat` и `uv run --frozen pytest tests/imports`.
Короткие команды сохраняют Allure
в `reports/allure/local`. При отсутствии `TEST_DATABASE_URL` API-тесты
завершаются ошибкой настройки, а не пропускаются. Разрешено только имя БД
`gis_test`; auth/chat удаляют только записи, созданные конкретной фикстурой.
Рабочий `.env` не используется для выбора БД. Миграции и справочники сохраняются.

Импорт заменяет слой целиком, поэтому `tests/imports/conftest.py` создаёт
для каждого случая схему `test_import_<uuid>`, применяет в ней существующую
миграцию и направляет туда соединения тестового приложения. После случая
схема удаляется. Данные в `public` тестами импорта не изменяются. Перед запуском
нужно выполнить обычный `alembic upgrade head`: он устанавливает PostGIS в `public`.
Пользователю тестовой БД нужны права создания/удаления схем и объектов в них.

`IMPORT-01…02` проверяют все шесть слоёв, вычисление площади/длины, большие ID,
повторную замену, поиск и устаревшую версию карточки. `IMPORT-03…09,13…14` —
доступ до разбора файла, отзыв прав во время запроса, строгий JSON/GeoJSON,
районы, конфликты, multipart, неизвестный слой, точные границы лимитов
и поток без `Content-Length`. `IMPORT-10…12` — полный откат при ошибке записи,
блокировку/таймаут и два одновременных импорта. При ошибках сравниваются
геоданные, геометрия, источники и метаданные версий до и после запроса.
Для проверки отката используется триггер, вызывающий ошибку на втором объекте;
триггер существует только во временной схеме.

После работы остановить одноразовую БД из корня репозитория:

```powershell
docker compose -f ops/compose.test.yml down
```

Фикстуры не подменяют авторизацию и SQL. Тестовый admin-маршрут существует
только в тестовом приложении. Импорт проверяется на настоящем маршруте
`/api/v1/admin/layers/{layer_code}/import`. Тестовая БД использует владельца
схемы; права ограниченной runtime-роли из `ops/grant-runtime.sql`, загрузка
через frontend, обрыв сетевого соединения и неопределённый результат COMMIT
требуют отдельной проверки. Реальные MLChat и restore этим набором не проверяются.

## Проверки работоспособности CI

В `ci/test_pipeline.py` находятся семь небольших проверок конфигурации проекта.
Одна фикстура в `conftest.py` читает `.gitlab-ci.yml`. Allure используется для
названий и шагов; отдельного теста самого Allure нет.

| Тест | Что защищает от случайного изменения |
|---|---|
| `test_workflow_rules` | Правила для ветки, MR и тега; приоритет подавления дубликата |
| `test_required_jobs` | Порядок этапов и обязательность quality/test/build без обхода через needs |
| `test_dependency_setup` | Проверка lock перед установкой зависимостей с --frozen |
| `test_quality_commands` | Наличие обязательных проверок Ruff, форматирования и mypy |
| `test_database_preparation` | Отдельный PostGIS service, подключения и двукратный запуск миграций |
| `test_tests_and_artifacts` | Запуск всей папки tests, сохранение результатов после ошибки и отдельный отчётный job |
| `test_package_build` | Команды сборки, установки wheel в отдельную среду, smoke и путь артефактов |

Эти тесты проверяют настройки нашего CI. Они не запускают вложенный pytest,
не собирают пакет повторно и не эмулируют GitLab runner. БД, Docker, Allure CLI
и Java для их локального запуска не нужны. Сборку, установку пакета и миграции
выполняют соответствующие jobs pipeline.

## Локальный запуск

Из `backend`, где лежит `pyproject.toml`:

```powershell
uv sync --frozen
uv run --frozen pytest tests/ci --junitxml=reports/ci.xml --alluredir=reports/allure/ci
```

Открыть Allure в браузере после этой команды (нужны Allure CLI и Java):

```powershell
allure serve reports/allure/ci
```

Для обычного локального запуска можно использовать короткую команду. Она
сохраняет результаты в `reports/allure/local`, как задано в `pyproject.toml`:

```powershell
uv run --frozen pytest tests/ci
allure serve reports/allure/local
```

`allure serve` создаёт отчёт и запускает временный сервер, открывая браузер.
Для остановки нажмите `Ctrl+C` в терминале.

Чтобы сохранить HTML-отчёт в один файл:

```powershell
allure generate reports/allure/ci --single-file --clean -o reports/allure-report
```

Откройте `reports/allure-report/index.html`. Новые файлы `test_*.py` с функциями
`test_*` в `tests` и её подпапках автоматически попадут в запуск CI.

## Приёмка pipeline после push

Это разовые сценарии проверки настройки CI, повторяемые при изменении jobs.
Они не входят в обычный pytest-прогон. Для каждого отрицательного сценария
используйте отдельную временную ветку от исправного состояния проекта.
В каталоге `ci/scenarios` лежат готовые патчи; они сами не выполняются.

Из **корня репозитория**, например для падения теста:

```powershell
git apply --check backend/tests/ci/scenarios/pytest-failure.patch
git apply backend/tests/ci/scenarios/pytest-failure.patch
```

Затем просмотрите diff, закоммитьте изменение и отправьте временную ветку.
После проверки патч можно снять командой `git apply -R` с тем же путём.
Каждый следующий сценарий выполняйте на исходном исправном состоянии.
Не объединяйте патчи: первый упавший этап скроет ошибки следующих.

| Сценарий | Подготовка | Ожидаемый результат в GitLab |
|---|---|---|
| Успешный push | Без патчей, push новой ветки | quality → ci-checks → build-package проходят; allure-report создаёт HTML; доступны wheel/sdist, JUnit и результаты Allure |
| MR без дубликата | Открыть MR для ветки и сделать новый push | Создаётся MR pipeline; второй branch pipeline для этого push не создаётся |
| Тег | Создать и отправить тестовый тег на исправном коммите | Создаётся tag pipeline и проходят обязательные jobs |
| Рассогласованный lock | `lock-mismatch.patch` | quality падает на uv lock --check; тесты и сборка не запускаются |
| Ошибка линтера | `lint-failure.patch` | quality падает на ruff check; тесты и сборка не запускаются |
| Ошибка форматирования | `format-failure.patch` | ruff check проходит, ruff format --check падает; тесты и сборка не запускаются |
| Ошибка типов | `type-failure.patch` | Ruff проходит, mypy падает; тесты и сборка не запускаются |
| Падение теста и отчёты | `pytest-failure.patch` | quality проходит, ci-checks падает; build-package пропущен; JUnit/Allure содержат падение; HTML доступен; pipeline остаётся красным |
| Ошибка подключения мигратора | `database-failure.patch` | PostGIS доступен, ожидание БД проходит, Alembic падает; pytest и build-package не запускаются |

В ошибках до запуска pytest результатов тестов нет: allure-report сообщает об
их отсутствии и не создаёт HTML. Это не меняет ошибочный статус pipeline.
Условный build-image выполняется отдельно, если включён ROOTLESS_BUILDKIT_ENABLED.

Для успешной сборки скачайте артефакт `build-package`: в нём должны быть `.whl`
и `.tar.gz`. Сам job проверяет установку wheel с зависимостями из lock и запуск
из отдельной среды вне исходников. Доступность скачивания проверяется в GitLab.

Для каждого сценария запишите ссылку на pipeline, commit, статусы jobs и результат.
Фактический запуск на runner, правила событий, блокировку jobs и доступность
артефактов подтверждает именно эта проверка после push. Локальный зелёный pytest
не доказывает эти свойства GitLab. Тесты не обращаются к GitLab API.
