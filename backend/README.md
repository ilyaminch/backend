# Backend ГИС-помощника

FastAPI, Python 3.12.12, PostgreSQL 16 / PostGIS 3.5. Зависимости зафиксированы
в `uv.lock`; версия uv — 0.9.5. Один процесс Uvicorn, без обращения к LLM
при ручной работе с картой. Реальный MLChat и выбранная модель ещё не подключены;
полный MVP не готов.

## Что реализовано

Префикс `/api/v1`:

| Метод | Путь | Назначение |
|---|---|---|
| GET | /health/live | Процесс работает |
| GET | /health/ready | БД доступна, ревизия миграции актуальна |
| POST | /auth/login | Вход, HttpOnly-cookie и CSRF-токен |
| GET | /auth/me | Пользователь и срок сессии |
| POST | /auth/logout | Отзыв сессии |
| GET | /layers | Реестр шести слоёв |
| GET | /layers/{layer_code}/features | Полный слой GeoJSON |
| GET | /objects/{object_id}?dataset_version=1 | Карточка тематического объекта |
| GET | /regions/{region_id}?dataset_version=1 | Карточка района |
| GET | /query-capabilities | Разрешённые поля, операции и лимиты |
| POST | /search | Строгий FilterV1: объекты или подсчёт по четырём районам |
| POST | /chat/sessions | Новый изолированный диалог |
| DELETE | /chat/sessions/{dialogue_id} | Удаление контекста и отмена запроса |
| POST | /chat/sessions/{dialogue_id}/messages | Шаг через подключаемый модуль MLChat |
| POST | /admin/layers/{layer_code}/import | Атомарная замена тематического слоя или четырёх районов |
| POST | /admin/demo/restore | Атомарное восстановление доверенного демонабора, JSON `{"confirm":true}` |

Все прикладные методы требуют входа. Обе роли читают одинаковый реестр;
`can_import` показывает право роли; импорт защищён admin и CSRF на сервере. Большие ID
и версии — строки. Nullable-поля сохраняются. При несовпадении версии карточка
возвращает 409; отсутствие объекта — 404. Ошибки содержат русский текст,
`request_id`, безопасные коды и `map_action=preserve`. Каждому запросу назначается
новый UUID, независимо от присланного заголовка. HTTP-журнал приложения
не сохраняет тела, query-параметры и секреты.

OpenAPI доступен по `/openapi.json`, Swagger — `/docs`. Проверяемый снимок схемы
находится в `../contracts/openapi.json`, пример пустого слоя — в
`../contracts/examples/empty-layer.json`. Изменение схемы согласуется с frontend;
затем обновляются снимок и тесты.

## Установка и запуск

Для работы frontend с реальным локальным API подготовлен отдельный
[Docker-профиль backend + PostGIS + MLChat](../ops/README.local.md).
Он использует `PUBLIC_ORIGIN=http://localhost:5173`, публикует API только на
`127.0.0.1:8000`, создаёт локальные user/admin и сохраняет БД в томе.
Модель и демоданные автоматически не устанавливаются.

Из каталога `backend`:

```powershell
uv lock --check
uv sync --frozen
Copy-Item .env.example .env
```

В `.env` замените заглушки подключения. Приложение загружает `.env` из текущего
каталога; пароли не входят в репозиторий. `COOKIE_SECURE=false` допустимо только
для локального loopback HTTP. Для сетевого профиля нужны HTTPS и secure-cookie.

Создайте БД `gis`, роли `gis_migrator` и `gis_runtime` с отдельными закрытыми
паролями. Мигратор должен владеть прикладными таблицами; PostGIS заранее создаёт
администратор либо мигратор имеет право создать расширение. Runtime не получает
DDL или административных прав. SQL-пример разрешений — `../ops/grant-runtime.sql`.
Для текущего API runtime читает данные и пишет `auth_sessions`, геоданные,
справочники и метаданные версий в пределах [grant-runtime.sql](../ops/grant-runtime.sql).
При обновлении до ZTOZ-115 владелец БД должен применить расширенные GRANT
из этого файла: restore заменяет также категории и источники. Права DDL
и изменения аккаунтов не выдаются.

Alembic **не читает** `.env`: задайте `MIGRATION_DATABASE_URL` переменной процесса
с приватными реквизитами, затем:

```powershell
uv run --frozen alembic upgrade head
```

Пользователи не создаются миграцией. CLI требует подключение мигратора/владельца
в `DATABASE_URL` на время этой команды; пароль вводится интерактивно:

```powershell
uv run --frozen python -m app.auth.cli demo_user --role user
uv run --frozen python -m app.auth.cli demo_admin --role admin
```

Верните runtime-подключение в `DATABASE_URL` и запустите:

```powershell
uv run --frozen uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1 --no-access-log
```

В запросе входа обязателен `Origin`, равный `PUBLIC_ORIGIN`, и JSON
`{"login":"demo_user","password":"введённый вами пароль"}`.
Для logout нужны тот же Origin и `X-CSRF-Token` из ответа входа или `/auth/me`.
Реальных геоданных в поставке пока нет: после миграции тематические слои пусты.
Не вставляйте случайные данные как демонабор Томска. CI использует отдельную
тестовую базу gis_test для проверки подключения и миграций.

## Первоначальная загрузка и восстановление демонабора

После получения принятого пакета установите его в доверенный каталог только
для чтения и задайте `DEMO_PACKAGE_DIR` в окружении сервера/CLI. Относительный
путь считается от рабочего каталога процесса. Для Docker смонтируйте пакет
read-only и задайте путь внутри контейнера; в wheel/образ реальный набор
пока не включён. Состав и схема манифеста описаны в [data/demo](../data/demo/README.md).
Затем под runtime-подключением с актуальными GRANT выполните:

```powershell
uv run --frozen python -m app.data_admin.demo_cli initialize
```

Команда предназначена только для БД без геоданных и без прежних импортов;
повторный запуск завершится `DATASET_NOT_EMPTY`, код выхода 1. Успех — код 0
и JSON с новой версией и числом объектов. Загрузка не запускается автоматически
при старте API. Отсутствующий пакет не мешает входу и ручной работе с картой.

Для восстановления администратор вызывает `POST /api/v1/admin/demo/restore`
с JSON `{"confirm":true}`, корректными `Origin`, cookie и `X-CSRF-Token`.
Путь/URL/архив запроса не принимаются. Сначала проверяются все SHA-256,
форматы, состав 500+4 и геометрия; одна транзакция заменяет все геоданные,
категории и источники, увеличивает dataset_version и обновляет все шесть слоёв.
Аккаунты, сессии входа и настройки LLM сохраняются. Повторный restore возвращает
тот же предметный набор с новой версией; старый результат поиска требует повтора.

Лимиты файлов/геометрии и lock wait используются из `IMPORT_*`; общий срок
`IMPORT_TIMEOUT_SECONDS` распространяется на весь пакет. После начала COMMIT
сервер ожидает реального подтверждения, что может продлить время ответа.
Если получен `RESTORE_RESULT_UNKNOWN`, перечитайте реестр/версию; POST
автоматически не повторяйте. Отсутствие пакета: 503 `DEMO_PACKAGE_UNAVAILABLE`;
невалидный пакет: 503 `DEMO_PACKAGE_INVALID`; ожидание блокировки: 503 `DATA_BUSY`;
истечение срока до commit: 504 `REQUEST_TIMEOUT`. До commit ошибка откатывает
все изменения, включая справочники и метаданные.

## Локальные проверки

```powershell
uv run --frozen ruff check .
uv run --frozen ruff format --check .
uv run --frozen mypy app
uv run --frozen pytest tests
uv build --no-sources
uv run --frozen python ../ops/smoke.py
```

Pytest включает критичные проверки авторизации/чата ZTOZ-111 и конфигурацию CI.
Для функциональных тестов нужны отдельная PostGIS-БД `gis_test`, миграции
и `TEST_DATABASE_URL`; подготовка описана в [tests/README.md](tests/README.md).
Реальная LLM не нужна. Только проверки CI можно запустить без БД и Docker:

```powershell
uv run --frozen pytest tests/ci --junitxml=reports/ci.xml --alluredir=reports/allure/ci
```

Для просмотра отчёта нужны Allure CLI 2.39.0 и Java 17+.
После полной команды выше открыть Allure в браузере:

```powershell
allure serve reports/allure/ci
```

После короткого запуска `uv run --frozen pytest tests`:

```powershell
allure serve reports/allure/local
```

Остановить сервер Allure можно через `Ctrl+C` в терминале.
Чтобы сохранить HTML-отчёт в один файл после полной команды:

```powershell
allure generate reports/allure/ci --single-file --clean -o reports/allure-report
```

В `tests/ci` находятся семь коротких проверок правил workflow, обязательности jobs,
зависимостей, quality, подготовки БД, запуска тестов/артефактов и сборки пакета.
Фикстура читает YAML; тесты используют шаги Allure. В `tests/auth` и `tests/chat`
находятся 12 критичных сценариев ZTOZ-111 (41 случай с параметризацией).
Для проверки самого runner
подготовлены отдельные отрицательные сценарии и чек-лист в
[tests/README.md](tests/README.md). Полное функциональное покрытие backend
и проверка демонабора 500+4 в текущий набор не входят.

## CI в GitLab

В корне лежит `.gitlab-ci.yml`. При push ветки/тега и merge request запускаются:
проверка lock-файла, Ruff, mypy, job `ci-checks` со всеми тестами из `tests` и отдельной
PostGIS service и двукратным применением миграций. Сборочный job создаёт wheel/sdist,
устанавливает wheel в отдельную среду с зависимостями из lock и выполняет smoke.
Ошибка обязательной
проверки делает pipeline неуспешным и блокирует следующие обычные этапы.
Отдельный этап report с `when: always` сохраняет HTML Allure даже после
падения тестов. Если pytest не запустился, HTML не создаётся.
JUnit и исходные результаты Allure доступны в артефактах jobs.
При открытом merge request второй branch pipeline подавляется.

Новые тесты в `tests` и её подпапках подхватываются автоматически: называйте
файлы `test_*.py`, функции `test_*`, а тестовые классы — `Test*`.
При добавлении тестов менять `.gitlab-ci.yml` не требуется.

Нужен Linux runner с поддержкой job images и services (Docker/Kubernetes
executor), доступом к PyPI и registry образов. Для shell/Windows runner эта
конфигурация не подходит. Действующие секреты БД и локальная LLM для CI не нужны;
пароль service относится только к одноразовой тестовой базе.

Сборка **пакета** включена всегда. Сборка **образа** подготовлена в job
`build-image`: включается переменной `ROOTLESS_BUILDKIT_ENABLED=true` после
подтверждения совместимости runner администратором. Используется rootless
BuildKit, без привилегированного Docker-in-Docker и сокета хоста; требуется
поддержка user namespaces и подходящие политики безопасности runner. Образ
сохраняется OCI-артефактом, в registry не отправляется. Образы закреплены по
версиям; перед выпуском нужно зафиксировать digest.

Первый pipeline возможен только после согласованного коммита/отправки в GitLab.
Файл CI сам по себе не доказывает доступность runner и успешное выполнение.
На текущем этапе нет CD и полного сетевого развёртывания MVP. Локальный backend
с PostGIS и установленным MLChat запускается отдельным Docker-профилем;
frontend этим профилем не запускается. Для установленной Ollama на Windows
доступен дополнительный `ops/compose.ollama.yml`; команды описаны в локальной инструкции.

## Следующие зависимости

Импорт и механизм первоначальной загрузки/restore реализованы отдельно от
frontend/MLChat. Готовый пакет500+4 поставлен в `data/demo/package`; исходники
вынесены отдельно. Инструкция — `data/demo/README.md` от корня репозитория.
Полная командная приёмка и проверка качества ответов ещё требуются.
Малый набор 28+4 для локальной интеграции и файлы импорта описаны в
`data/verification/README.md` (путь от корня репозитория); это отдельная поставка.
Фильтры, поиск, районные counts, временные диалоги и HTTP-адаптер LLM реализованы
в ZTOZ-100. MLChat подключён в локальном Docker-профиле; для Qwen3.5 9B
в Ollama подготовлена конфигурация поставщика MLChat 0.1.3. Совместная приёмка на реальных данных
ещё требуется. Для подключения демопакета нужен также `ops/compose.demo.yml`.
В окружении без фабрики сообщения получают DIALOGUE_UNAVAILABLE,
без настроенной модели её клиент возвращает LLM_UNAVAILABLE; поиск работает
независимо. Для count_by_region нужны ровно четыре загруженных района, иначе
503 DATA_BUSY. Искусственные свойства/объекты полученной демопоставки явно отмечены
в метаданных.
Численные лимиты входа/чата согласованы 18.10.2026, импорта — 21.10.2026;
значения задаются в `.env.example` и публикуются в `/query-capabilities`.
У приложения одна реплика и один worker. Argon2id: time_cost=3,
memory_cost=65536 KiB, parallelism=4; замер на целевом сервере ещё требуется.
Frontend и регрессионные автотесты принадлежат коллегам. CI/CD и tests в задачах
ZTOZ-106/100/107 не менялись.
